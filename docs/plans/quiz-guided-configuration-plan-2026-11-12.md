# 补充试题要求：六步引导执行方案

日期：2026-11-12。状态：需求已确认，方案待实施。本文件只规划改造，不表示功能已经完成。

## 1. 目标与范围

将聊天中的“补充试题要求”从现有两步表单，改为六个逻辑步骤、每次一个问题的引导。助手持续从自然语言中提取配置，已明确且有效的信息直接跳过；全部要求齐备后，在用户消息气泡中呈现汇总，并立即开始生成。

六步为：用途 → 资料 → 题型 → 题量 → 难度 → 总分。即时小练在用途确认后分流，检索资料并直接在聊天中出题，不创建正式试卷。

本次交付包括聊天引导、即时小练分流、模型参数提取、题量推荐、状态恢复、用户气泡汇总和必要的接口及测试调整。正式试卷继续使用现有异步生成、草稿与后续作答能力。

## 3. 六步交互规则

| 步骤 | 问题与控件 | 完成条件与行为 |
| --- | --- | --- |
| 1 用途 | “你想生成一套试卷，还是做即时小练？”；单选 | 明确“试卷/模拟卷”等可直接进入试卷流程；明确“即时小练/直接问我一题”等直接检索；“帮我出题”等用途含糊时才询问 |
| 2 资料 | “使用哪些资料？”；单选 | “当前允许范围的全部可用资料”或“指定资料”；点击指定资料立即打开原文件选择器，确认有效文件后完成 |
| 3 题型 | “需要哪些题型？”；复选 | 单选、多选、判断、填空、简答、计算、证明；至少一种，点击“继续”统一确认，不能第一次勾选就跳走 |
| 4 题量 | “每种题型出多少题？”；方案单选与自定义 | 模型给出 2～3 套有效搭配，展示各题型数量及总题数；自定义允许逐题型输入；确认后形成正式蓝图 |
| 5 难度 | “试卷难度如何？”；单选 | 基础、标准、进阶、混合，对应现有难度枚举 |
| 6 总分 | “试卷总分是多少？”；数值填空 | 大于 0、不超过 10000，支持有效小数；最终动作显示“完成并生成” |

每一步都允许用户改用文字回答，并一次补充多个后续参数。只出现当前需要回答的一个问题；题量自定义属于同一个逻辑问题，不拆成额外步骤。

展示当前问题名称和待补充问题数量，避免跳步后出现误导性的连续“第几步”。提供返回修改、取消本次配置；已完成信息可通过摘要查看并修改。

文件选择器取消时保留原资料配置；首次选择指定资料后取消，不得自动改成全部资料。指定资料最终至少一份，避免空列表与“全部资料”的现有语义混淆。

## 4. 自动提取与步骤调度

### 4.1 结构化状态

建议增加独立的引导状态，放在现有 conversation 的待配置数据中；继续把最终出卷字段保存在 `quiz_input`。字段名在实施时统一到前后端合同。

| 状态 | 内容 |
| --- | --- |
| `mode` | 未确定、试卷、即时小练；不能使用旧的默认 practice 值代替用户用途判断 |
| `selected_question_types` | 用户选定的题型，允许尚无每类数量 |
| `requested_total_count` | 用户只给出总题数时保存，不虚构每类配额 |
| `quiz_input` | 已收集的资料、范围、蓝图、难度、总分等正式参数 |
| `field_origins` | 记录用户明确输入、用户选中的推荐、上下文继承、产品默认等来源 |
| `next_step` | 后端计算的下一个缺失或冲突步骤；前端不自行推断生成条件 |
| `quantity_options` | 本轮有效推荐及其依据的资料、题型、已知总量快照 |
| `revision` | 状态版本，防止旧请求覆盖新选择，区分正常刷新与旧标签页提交 |

单独保存题型和总量很关键：现有 `blueprint` 要求每类已有数量，无法自然表达“要单选和简答，数量还没决定”。

### 4.2 每轮处理

1. 接收文字回答或控件提交；控件提交直接映射结构化字段，不额外依赖模型解释选项文字。
2. 自然语言经模型提取增量参数，结合当前问题解释“第二个”“100”等简短回答。
3. 合并配置并校验，优先级为本轮明确修改 > 之前用户确认 > 可兼容的上下文继承 > 产品默认。
4. 冲突时定位到对应问题，一次只追问一个需要消解的冲突。
5. 无冲突时按六步顺序查找缺项，跳过已经有效的信息，返回下一个问题。
6. 全部齐备时，服务端执行最终校验、持久化汇总消息和提交生成任务，返回消息与任务标识。

最新输入覆盖旧值，但不能扩大当前对话允许的资料或章节范围。模型建议只有在用户选择后才能成为已确认配额。

### 4.3 修改与失效规则

- 修改资料或题型：丢弃尚未确认的旧推荐，重新生成选项。
- 修改题型：删除被取消题型的配额；新增题型尚无数量时回到题量步骤，保留其余已确认数量。
- 修改资料：复核已有配额与知识点限制；仍然有效的用户明确配置保留，无须全部重问。
- 只给出总题量：题量推荐必须满足该总量。题型与总量都没给全时，不提前猜配额。
- 同时给出“共 10 题”与合计 12 题的分项：追问题量冲突，不静默选择其中之一。
- 用户明确说“按你建议的数量”：视为授权采用推荐；仍须由服务端校验后进入后续步骤。

## 5. 六步以外字段的处理建议

以下为本方案建议采用的产品默认，需要在实现和合同文档中明确，不能继续保持为隐藏必填项。

| 字段 | 建议策略 |
| --- | --- |
| 出题章节/知识点 | 继承用户输入和当前对话约束；没有限制时采用当前课程允许范围，不追加范围步骤 |
| 计时 | 用户明确要求或有效考试配置已有时沿用，否则不限时；明确限时但缺分钟时仅对该条件补问 |
| AI 补充 | 默认不允许，资料不足时说明并请用户调整；用户明确授权才允许，不能因资料不足自行开启 |
| 独立导入题 | 当前能力仅支持不纳入；按能力规则处理，明确要求纳入时提示现有限制 |
| 重点、排除项、来源类别、关联考试 | 从用户输入或兼容上下文保留；没有时不增加固定步骤 |
| 总分 | 六步引导的必填项；旧 API 和已保存配置是否必填维持兼容，不贸然全局改 schema |

由引导层形成可交给原 resolver 的完整输入，避免在全部旧接口中无差别放宽校验。对原先要求“必须明确选择”的 AI/导入题/计时行为，要更新为本引导入口的产品策略，并将实际采用的值反映到最终配置及摘要。

六步是正常流程。用户输入冲突、文件同名、明确限时却未给分钟等情况，允许针对当前问题进行必要澄清，不新增固定第七步。

## 6. 题量推荐

推荐使用用户所选题型、允许资料中的可用知识点与检索摘要、用户已指定的总量和每类数量。不必为推荐提前执行正式试卷生成，也不能声称已通读所有文件。

推荐由模型生成结构化候选，再由后端验证：

- 仅包含已选题型，且每种已选题型至少一题；题量为正整数，总计 1～100。
- 遵守用户明确的总题数、分项配额及现有知识点配额限制。
- 不重复，展示简短推荐理由；不依赖尚未询问的难度、总分才可成立。
- 只能存在两套有效搭配时展示两套，不为凑三套输出非法方案。
- 已知约束使题量只有唯一解时，直接视为题量已明确并跳过；不可行时只追问冲突。

例如已选“单选、简答”且没有额外限制时，可展示“单选 6 + 简答 2，共 8 题”“单选 10 + 简答 3，共 13 题”“单选 15 + 简答 5，共 20 题”，以及“自定义”。这是交互示例，不写死为所有课程的推荐。

模型失败或候选校验失败时采用有限重试；仍失败则展示错误并保留自定义入口，不制造假推荐、不丢失前面配置。

## 7. 即时小练分流

即时小练复用课程资料选择、权限约束和知识检索能力，通过专用出题指令在对话中返回题目。不要直接调用会创建快速测验会话的旧接口来冒充本需求的聊天出题。

处理顺序：识别即时练习意图 → 继承或解析本次资料/知识点范围 → 检索实际资料片段 → 基于片段给出题目及必要来源。

- 不进入试卷六步的其余问题，不创建正式试卷、草稿或试卷生成任务。
- 没有指定题量时建议先出 1 题，便于即时作答；明确题量和题型则按可支持的请求处理。
- 默认先展示题目，答案解析待用户作答或主动索要时再给出。
- 没有可用资料或检索依据不足时说明实际情况，不伪造引用、不换用范围外资料。
- 从试卷配置切换为即时小练时，清除未提交的试卷引导状态，保留适用的资料限制。
- 即时题目和用户作答继续保存在聊天记录中；本次不扩展独立计分、排行榜或正式考试能力。

“默认一题、先题后答”属于本方案建议的即时练习交互默认，不是现有实现事实。

## 8. 用户汇总气泡与生成提交

收集完成后，由服务端根据已校验配置生成确定性的汇总文本，前端以用户气泡展示。例如：

> 生成试卷：使用《TCP 讲义》《网络习题》；单选题 8 道、简答题 2 道，共 10 题；基础难度；总分 100 分；不限时；仅依据所选资料，不纳入独立导入题。

如有章节、知识点、重点、排除项或 AI 补充授权，汇总一并显示。全部资料模式明确写“当前允许范围的全部可用资料”，实际使用的文件列表继续留在服务端快照中。

- 不再只显示现有的“生成试卷”四个字，也不要求用户重新打字复述配置。
- 不增加独立汇总确认步骤。最后一个缺项提交成功后，汇总呈现并立即排队生成；首次输入已经齐备时同样适用。
- 汇总作为用户本次配置的系统整理结果保存，避免把它当成模型新推断的用户偏好；可保存配置汇总类型及结构化关联。
- 保留用户原始文字消息。若原始消息已经展示，最终汇总是独立整理气泡，不覆盖历史输入。
- 复用现有幂等机制，汇总消息与任务关联，处理重复点击、网络重试、刷新和旧请求，避免重复消息、重复排队。
- 数据提交与任务排队的一致性沿现有事务及锁顺序实现；失败可恢复，不出现“看起来已提交，实际没有任务”的静默状态。

## 9. 前后端实施划分

### 阶段 A：引导合同与后端状态

交付：可表达未知用途、题型未配额、总题量、当前问题、推荐方案与版本的请求/响应合同；服务端引导调度模块。

建议新增 `src/final_review/quiz_guidance.py` 集中处理合并、下一问题、失效规则和提交条件，避免继续扩大 `api.py`。扩展 `schemas.py`、conversation 待配置序列化与读取接口，兼容旧 `pending_quiz`；确认 JSON 存储是否足够，确需表结构变化时才添加迁移。

完成标志：后端测试可完整驱动六步、跳步、返回修改和重启恢复；收集动作不会提前排队。

### 阶段 B：意图识别与即时小练

交付：修改 `classify_chat_intent` 及 dispatch 分支，取消“所有出题一律 draft”的规则。模型输出包含真实用途与增量参数，避免默认 practice、默认题型被误认为用户明确选择。

普通“模拟试卷是什么意思”等讨论继续作为问答；含糊出题请求进入用途问题；即时小练强制经过检索再出题。最终模式及步骤由服务端校验控制，不能只依赖提示词。

完成标志：普通问答、用途澄清、正式试卷、即时练习四条路径可独立验证。

### 阶段 C：题量推荐与配置落地

交付：在 `llm.py` 等现有模型层增加结构化题量推荐能力；候选验证、去重、缓存和失效处理；引导默认策略转换；总分引导必填校验。

最终配置继续通过 `resolve_quiz_config` 和现有生成合同校验。只在所有必要问题已解决后调用现有 `enqueue_quiz`。

完成标志：推荐数量与生成蓝图一致；非法候选不会进入前端可选列表；自定义和模型异常都有可用处理路径。

### 阶段 D：聊天引导界面

交付：新增聊天专用引导组件，如 `QuizGuidanceCard.tsx`，复用现有资料选择器和主题；调整 `ChatHome.tsx` 的输入禁用逻辑、消息恢复和提交处理。

配置期间允许用户输入和点击卡片，两种操作进入同一状态；请求处理中防止并发覆盖，响应需核对 conversation 和状态版本。多选必须显式继续；单选确认后可自动推进；自定义和分数输入有明确提交动作。

独立“模拟测验”生成入口本轮保留现有组件和直接生成语义，避免无关扩展；共享类型可抽出为公共文件，聊天新组件和旧入口共用正式配置合同。若后续要统一入口，另行规划。

完成标志：桌面和约 390px 手机宽度均一次只展示一个问题；文件弹窗取消不丢状态；配置中可自然语言补充。

### 阶段 E：汇总、恢复与联调

交付：服务端持久化配置汇总消息并关联生成任务；前端使用返回的规范消息更新时间线；刷新恢复待配置状态、已收集参数、已确认题量和最终任务。

文本框未提交的草稿可仍为本地临时输入；已经确认的选项和参数必须保存到服务端。旧会话缺少引导状态时转换为兼容初始状态，已有试卷和历史题卡继续可读取。

完成标志：完成最后一个缺项后只出现一条最终汇总，只创建一个生成任务；取消、失败、刷新后行为可解释且可恢复。

### 阶段 F：验证与文档

交付：更新自动测试、手动测试说明及 `docs/quiz-generation-contract.md`，说明正式试卷和即时小练的新分流、产品默认、跳步、总分要求与确认语义。

实施按 A → B → C → D → E → F 推进。当前工作区已有多处未提交改动，实施需基于当前实际文件增量修改并保护这些改动，不覆盖或回退。

## 10. 验收清单

| 场景 | 预期结果 |
| --- | --- |
| “帮我出些题” | 只询问用途，不直接选为正式试卷或即时练习 |
| “用全部资料生成一套试卷” | 跳过用途、资料，进入题型 |
| “按这两份讲义出 8 道单选、2 道简答，基础难度，100 分试卷” | 文件可唯一定位且约束有效时跳过全部问题，呈现汇总后直接生成 |

| 正在选择资料，输入“全部资料，基础难度，总分 100” | 更新三个参数，只继续询问尚缺题型和题量 |
| 勾选单选题后继续勾选简答题 | 不会在第一次勾选后离开题型步骤 |
| 点击指定资料、勾选文件、确认 | 弹窗立即打开；回到引导显示文件摘要，继续下一缺项 |
| 文件弹窗取消或没有选中文件 | 保留原有效选择；没有原选择时仍停在资料问题 |
| 改变题型或资料 | 过期推荐失效；保留仍有效的已确认字段 |
| 推荐失败 | 显示可理解错误，允许重试或自定义，无配置丢失 |
| 难度与总分已在原话给出 | 后续不会再次询问对应问题 |
| 总分为空、0、负数、非数字或超上限 | 不能提交生成，提示修改；有效小数可接受 |
| 题数超限、总量与配额矛盾、范围越界 | 后端拒绝，定位相关问题，不静默改变用户要求 |
| “即时小练，直接问我一道 TCP 的题” | 检索后聊天出题，不出现正式配置或创建试卷任务 |
| 无可检索资料 | 明确说明依据不足，不冒充基于资料出题 |
| 连点最终提交、网络重试或生成后刷新 | 一条最终汇总、一个任务，恢复相同状态 |
| 配置中刷新、切换聊天后返回 | 恢复已确认数据，正确定位下一个问题，不混入别的会话 |
| 取消试卷配置 | 清除当前待配置状态，保留历史聊天；之后可正常发送消息 |
| 独立生成入口、原试卷草稿和正式作答 | 保持已有功能可用 |

验证分层：先运行引导、意图分流、配置校验、生成合同相关后端测试；再运行前端构建与相关 E2E；因涉及共用 dispatch 与生成链路，交付前执行项目要求的完整后端检查。实际模型另做少量自然语言补参、推荐和即时检索冒烟，分别报告确定性测试与真实模型结果。

## 11. 完成定义

用户既可全程点击选项，也可在任意一步用一句话补齐多项要求；系统只问缺失信息。正式试卷在配置齐备后展示完整用户汇总并开始现有生成流程，即时小练直接基于检索在聊天出题。两条路径均遵守资料边界，状态可恢复，无重复任务，并通过上述验收。
